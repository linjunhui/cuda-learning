### **Day 1：从“能跑”到“跑满” —— 访存瓶颈与 Nsight Compute 实战**

**【面试题】**

> “你手写过 Softmax 算子。请问：对于一个常见的 （序列长度  注意力头数）的矩阵，传统的 Softmax 为什么是 **Memory-bound（访存受限）** 的？
答:
多轮访存（Multiple Passes）： 朴素实现通常需要三次遍历数据：第一次找 $max(x)$，第二次算 $\sum e^{x-max}$，第三次做归一化。即使在 GPU 内部完成，如果不做融合，中间结果（如每个元素的指数值）必须反复写回显存（VRAM）再读出来。显存带宽 vs 计算量： Softmax 的计算主要涉及减法、指数（$exp$）和除法。相比于矩阵乘法（GEMM）这种 $O(n^3)$ 计算量、 $O(n^2)$ 访存量的 $O(n)$ 复杂度操作，Softmax 是典型的 $O(n)$ 计算量对 $O(n)$ 访存量。在 A100 等现代 GPU 上，显存带宽（约 $2\text{ TB/s}$）远慢于其理论算力，导致硬件大部分时间在等待数据搬运。
> 如果让你利用 **Online Safe Softmax** 算法进行优化，你如何通过 `Nsight Compute` 证明你的优化减少了对 Global Memory 的访问？并请说明在 CUDA 层面，你是如何处理 **SRAM (Shared Memory)** 溢出问题的。”

### **【指导：如何去实践】**

这题不要求你重新写一遍，而是要求你**量化你的性能指标**。

#### **第一步：环境准备（1小时）**

1. **代码准备：** 准备一份你手写的 Online Safe Softmax 代码（即：在一次 Pass 中完成最大值查找、累加和归一化）。
2. **基准对比：** 准备一份最原始的、分三次 Kernel（FindMax -> Sum -> Div）跑的 Softmax 代码。

#### **第二步：性能剖析（核心环节：3小时）**

1. 使用 `ncu` (Nsight Compute) 运行这两个 Kernel：
```bash
ncu --metrics smsp__sass_data_pipe_lsu_mem_wm_inst_fills.sum,gpu__compute_memory_throughput.avg_pct_of_peak_sustained_elapsed ./your_binary

```


2. **观察指标：**
* 查看 **Memory Chart**：对比两个版本对 DRAM 的读写带宽占用。
* 查看 **Roofline Model**：确认你的算子点是在斜率（访存受限）上还是在顶部（计算受限）上。



#### **第三步：深挖 Shared Memory（2小时）**

* **实践：** 尝试把数据加载到 Shared Memory 中进行处理。
* **思考：** 如果 （头尺寸）非常大（比如超过了 48KB/96KB 的硬件限制），你的代码会挂掉吗？
* **优化：** 学习并尝试 **"Tiling Softmax"**（分片处理），确保你的算子能处理任意长度的头。

#### **第四步：总结产出（1小时）**

写一段 300 字左右的复盘，模仿面试语境：

> “我通过 ncu 分析发现，原始实现因为多次读写 Global Memory 导致带宽利用率达到 90%+ 但计算单元处于饥饿状态。通过 Online 算法结合 Shared Memory 缓存，我将访存次数从 3 次降低为 1 次，吞吐量提升了 XX%...”
