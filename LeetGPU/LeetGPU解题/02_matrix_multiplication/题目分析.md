# 典型的GEMM

## 思路梳理
### 1. 先分析形状
- A (M x K), B (K x N) -> 计算结果 C(M x N)
- 每个线程计算C中的一个元素 C(i, j), 需要 A的第i行和B的第j列

### 2. 分TILE，利用共享内存
- TILE (32 x 32)的正方形
- 一个TILE在 A 上横向滑动(stride=32) 与 一个TILE在B上竖向滑动(stride=32) 进行矩阵乘法，边滑动进行矩阵乘法，边累加
- 那么就是(TILE_SIZE, K)的矩阵与(K, TILE_SIZE) 的矩阵进行矩阵乘法，结果是 (TILE_SIZE, TILE_SIZE)
- 那么i,j 的取值就是32 的整数倍

### 3. 关于shared memory的bank conflict分析
- A的TILE与B的TILE进行矩阵乘法，A的TILE的行乘以B的TILE的列, B读取的时候一整列，B的TILE 一行32个元素，占128字节，按列读取，出现严重的bank conflict
- 解决方法1：B的TILE形状设计为 (TILE_SIZE, TILE_SIZE + 1), 打破一行32个元素
- 解决方法2：转置， 读取B到TILE的时候，将B的列，按行存储到TILE

- 1. C的形状(M, N), 那么这里考虑 block_size 二维
- 2. TILE_SIZE = 32, block_size(32, 32) 刚好1024个线程，也到达一个block线程的上限了
- 3. 工程中可能优先 考虑 256线程， (16, 16)

- 2. 加载一个 TILE 到 shared memory
- 3. 每次只能加载一个TILE， 但是计算一个元素需要的是A的一整行和B的一整列, K个元素
- 3.1 这里要计算 TILE个数 TILE_NUM = (K + TILE_SIZE - 1) / TILE_SIZE
